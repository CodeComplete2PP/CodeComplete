## 30장: 프로그래밍 도구

### 30.1 설계 도구

- 다이어그램, 모델링, 데이터 사전 도구는 설계를 시각화하고 일관성을 검사함
- 도구가 만드는 산출물보다 설계 문제를 발견하고 팀이 의사소통하는 효과가 중요함

### 30.2 소스 코드 도구

- 편집기와 IDE의 탐색, 검색, 자동 완성, 리팩터링 기능으로 기계적인 작업을 줄임
- 다중 파일 검색과 정규 표현식으로 변경 영향과 반복 패턴을 찾음
- 차이 비교, 병합, 버전 관리 도구로 변경을 검토하고 복구함
- 코드 생성기와 전처리 도구는 반복 코드를 줄이지만 생성 규칙과 결과를 함께 관리함
- 정적 분석, 스타일 검사, 컴파일러 경고로 실행 전에 결함을 찾음

### 30.3 실행 코드 도구

- 디버거로 제어 흐름과 상태를 관찰하고 프로파일러로 실제 병목을 측정함
- 테스트 프레임워크, 커버리지, 메모리 검사 도구로 실행 결과와 자원 사용을 검증함
- 도구의 결과를 맹신하지 않고 무엇을 측정하며 무엇을 놓치는지 이해함

### 30.4 도구 중심 환경

- IDE와 통합 환경은 편집, 빌드, 테스트, 디버깅을 한 흐름으로 연결함
- 특정 도구에 종속되더라도 빌드와 테스트가 재현 가능하고 자동화 가능한지 확인함

### 30.5 직접 프로그래밍 도구 만들기

- 반복 작업의 수작업 비용이 도구 작성과 유지보수 비용보다 크면 작은 도구를 만듦
- 범용 도구보다 현재 문제를 정확히 해결하는 단순한 스크립트가 더 효과적일 수 있음
- 직접 만든 도구도 오류 처리, 테스트, 문서화가 필요함

### 30.6 도구 환상

- 새로운 도구가 요구사항, 설계, 사람, 프로세스 문제를 자동으로 해결하지는 않음
- 기능 목록보다 실제 병목, 도입 비용, 팀의 숙련도, 장기 유지 가능성을 기준으로 선택함

### 요점 정리

- 도구는 개발자의 판단을 대신하지 않고 반복 작업과 관찰을 돕는다.
- 좋은 도구 선택은 기능 목록보다 프로젝트의 실제 문제와 사용 방식에 달려 있다.

### 참고 자료

- 도구별 사용법은 빠르게 변하므로 현재 환경의 공식 문서와 팀의 실제 측정 결과를 함께 참고함
