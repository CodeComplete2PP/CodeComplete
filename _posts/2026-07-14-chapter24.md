## 24장: 리팩터링

### 24.1 소프트웨어 진화의 종류

- 프로그램은 새 기능 추가, 결함 수정, 환경 변화, 품질 개선을 거치며 계속 진화함
- 초기 구현은 완벽한 구조가 아니며 변경 과정에서 구조가 자연스럽게 나빠질 수 있음
- 기능 변경과 구조 개선을 구분해 각각의 목적과 검증 방법을 명확히 함

### 24.2 리팩터링 소개

- 리팩터링은 외부에서 관찰되는 동작을 유지하면서 내부 구조를 개선하는 변경임
- 중복, 긴 루틴, 큰 클래스, 긴 매개변수 목록, 서로 다른 변경 이유가 주요 신호임
- 새 기능 추가나 결함 수정 전에 코드를 변경하기 쉬운 형태로 정리함
- 리팩터링 자체를 끝없는 미화 작업으로 만들지 않고 실제 변경과 이해 비용을 줄이는 데 사용함

### 24.3 구체적인 리팩터링

- 반복되는 코드를 루틴이나 클래스로 추출함
- 긴 루틴을 응집도 높은 작은 루틴으로 나누고 이름으로 의도를 설명함
- 복잡한 조건을 단순화하고 boolean 루틴, 테이블, 다형성을 적용함
- 데이터와 그 데이터를 사용하는 동작을 같은 클래스로 옮김
- 매직 넘버를 이름 있는 상수로 바꾸고 변수와 루틴 이름을 정확하게 고침
- 사용하지 않는 코드, 불필요한 중간 계층, 전달만 하는 루틴을 제거함

### 24.4 안전한 리팩터링

- 한 번에 하나의 작은 변경을 수행하고 매 단계 컴파일과 테스트를 실행함
- 변경 전 동작을 보호할 테스트가 부족하면 먼저 특성 테스트를 마련함
- 리팩터링과 기능 변경을 한 단계에 섞지 않아 실패 원인을 쉽게 찾게 함
- 버전 관리, 코드 리뷰, 정적 분석으로 되돌리기와 검증을 지원함

### 24.5 리팩터링 전략

- 오류가 생기기 쉬운 코드, 자주 바뀌는 코드, 이해하기 어려운 코드를 우선함
- 작은 개선을 일상적으로 수행해 대규모 재작성 필요성을 줄임
- 구조가 근본적으로 맞지 않거나 리팩터링 비용이 재작성보다 크다면 재설계를 별도로 판단함

### 요점 정리

- 리팩터링은 큰 재작성보다 작고 검증 가능한 구조 개선의 반복에 가깝다.
- 테스트가 외부 동작을 보호할 때 안전하게 리팩터링할 수 있다.

### 참고 자료
