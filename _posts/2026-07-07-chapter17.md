## 17장: 특이한 제어 구조

### 17.1 루틴의 여러 반환 지점

- 반환 지점이 하나면 루틴의 제어 흐름과 정리 작업을 추적하기 쉬움
- 그러나 오류 조건을 초기에 반환하면 정상 경로의 중첩을 줄이고 코드를 단순하게 만들 수 있음
- 반환 지점을 기계적으로 하나로 제한하기보다 가독성, 오류 가능성, 자원 정리 요구를 함께 판단함
- 여러 반환을 사용할 때는 루틴 앞부분의 경비 절처럼 예측 가능한 위치에 둠
- 잠금, 파일, 메모리 같은 자원이 모든 경로에서 정리되는지 확인함

### 17.2 재귀

- 재귀는 문제를 같은 형태의 더 작은 문제로 표현할 수 있을 때 적합함
- 모든 재귀 루틴에는 진행을 멈추는 명확한 기저 조건이 있어야 함
- 재귀 호출마다 입력이 기저 조건에 가까워지는지 확인함
- 호출 깊이와 스택 사용량이 입력 크기에 따라 얼마나 증가하는지 검토함
- 단순 반복으로 더 명확하고 안전하게 표현할 수 있다면 반복문을 선택함
- 재귀가 중복 계산을 만든다면 메모이제이션이나 다른 알고리즘을 검토함
- 간접 재귀는 호출 관계가 숨겨지기 쉬우므로 특히 신중하게 사용함

### 17.3 `goto`

- `goto`는 임의의 위치로 제어를 옮겨 정상적인 위에서 아래 흐름을 깨뜨림
- 대부분의 경우 조건문, 반복문, 루틴 호출로 더 분명하게 표현할 수 있음
- 깊게 중첩된 구조에서 한 번에 빠져나오거나 C의 공통 정리 구역으로 이동하는 제한된 경우에는 실용적일 수 있음
- 사용해야 한다면 앞으로만 이동하고, 짧은 범위 안에서, 하나의 분명한 목적으로 제한함
- `goto`를 없애기 위해 상태 변수와 중첩을 과도하게 추가해 코드가 더 복잡해지는지도 비교함

### 17.4 특이한 제어 구조에 대한 관점

- 제어 구조의 선택 기준은 교조적인 금지보다 전체적인 이해 가능성임
- 정상 흐름이 분명하고, 진입점과 종료점이 예측 가능하며, 변경 시 영향 범위를 추적할 수 있어야 함
- 특이한 구조가 꼭 필요하다면 사용 이유와 제약을 코드 가까이에 남김

### 참고 자료

- 구조적 프로그래밍과 제어 흐름 복잡성은 19장에서 더 자세히 다룸

### 요점 정리

- 여러 반환 지점은 신중히 사용하되, 경비 절로 복잡성을 줄이는 경우에는 단일 반환보다 나을 수 있다.
- 재귀는 문제 구조와 자연스럽게 맞고 기저 조건과 자원 사용이 분명할 때 사용한다.
- `goto`는 대부분 피할 수 있지만, 대안보다 명확한 제한적 상황까지 기계적으로 금지할 필요는 없다.
- 제어 구조의 궁극적인 기준은 프로그램의 가독성, 신뢰성, 수정 용이성이다.
